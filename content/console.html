01

제품과 담당 범위

환자 상태와 수면·처방·기기 이력, 환자별 청구내역을 관리하는 웹입니다. 저는 업무 조건을 정리하고, PostgreSQL 모델과 제한 함수, API·DB 권한 계약, 백엔드·배치를 주로 담당했습니다. 화면 구성과 프런트엔드 구현은 협업 결과입니다.

아래에서는 환자 상세의 청구내역서를 사례로 설명합니다. 현재 자료로 계산한 금액과 저장된 청구 결과를 구분하고, 관리자가 검토한 근거로 발행하며, 수정 이후에도 기존 발행본을 보존해야 하는 기능입니다.

화면 자료
환자·기기 화면은 실제 UI에 가상 API 응답을 넣어 촬영했습니다. 청구내역서는 실제 컴포넌트의 개발용 가상 자료로 발행·재발행을 재현했습니다. 운영 환자 데이터나 운영 API에 연결하지 않았습니다.
02

관리자 UI

환자 대시보드, 환자 상세, 기기 대장을 한 섹션으로 모았습니다. 각 화면을 선택하면 상세 설명과 원본 이미지를 볼 수 있습니다.

환자 대시보드

처방 만료, 사용시간, AHI 지표와 환자 검색·필터를 제공합니다. 집계 기간과 환자 범위를 맞추고, 수집되지 않은 자료와 실제 사용 0을 구분하는 조회 계약을 다뤘습니다.

환자 상세와 이력

수면 추이, 현재·과거 처방, 기기 배정 이력을 연결합니다. 현재 상태와 과거 기록을 구분하고, 환자별 청구내역서도 이 화면에서 확인합니다.

기기 대장

기기의 현재 상태와 사용자, 배정·케어 이력을 확인합니다. 현재 배정만 덮어쓰지 않고 이력을 관리하며, 조회 결과가 해당 업체의 기기와 환자를 가리키도록 계약을 맞췄습니다.

03

청구내역서의 API 흐름

환자 상세에서 월별 청구내역을 열면 현재 자료의 계산 결과, 저장된 청구 내역, 추가 금액과 발행 이력을 함께 조회합니다. 조회 화면에 금액이 보이는 것과, 그 금액으로 내역서를 발행할 수 있는 상태를 구분했습니다.

  1. 1환자 상세조회 · 발행 준비 · 발행
  2. 2콘솔 API인증된 운영자·업체 확정
  3. 3NHIS 업무 API계산·청구 근거 재검사
  4. 4DB 제한 함수권한·상태 검사 후 변경
브라우저가 호출하는 API서버에서 이어지는 처리
GET /api/billing-statements관리자 조회 함수로 저장된 청구·추가 금액·발행 이력을 읽고, 업무 API에서 현재 계산 결과와 발행용 미리보기를 가져옵니다.
POST /api/billing-statements/ready/billing/patient-statements/ready를 거쳐 runtime.transition_patient_billing_statement를 READY로 호출합니다.
POST /api/billing-statements/issue같은 업무 API와 제한 함수에서 검토한 근거·준비 상태를 다시 확인하고 ISSUED로 전환합니다.
POST /api/billing-statements/charges이월금·기타 금액 조정은 carebot.mutate_patient_billing_charge로 처리합니다. 반납비 조정은 별도의 제한 함수를 사용합니다.

현재 계산과 저장된 청구의 구분

현재 계산 결과는 청구 실행 전에도 조회할 수 있습니다. 계산 캐시를 저장할 수는 있지만, 조회가 Claim·청구 주기·내역서를 생성하거나 변경하지는 않습니다. 계산 API가 실패하면 저장된 금액을 현재 계산값으로 대신 표시하지 않습니다.

발행 요청에서는 검토한 계산의 calculation_source_hash와 발행 근거의 source_hash를 함께 확인합니다. 현재 계산 근거가 달라졌거나 계산 금액과 저장된 청구 금액이 맞지 않으면 발행을 중단합니다.

04

제한 함수와 정합성

청구내역서의 생성·상태 변경을 제한 함수에 모았습니다. API의 입력 검사에 더해 DB에서도 운영자의 역할과 업체, 환자·청구월의 관계, 청구 완료 여부와 근거 변경을 확인합니다.

함수담당하는 처리
runtime.preview_patient_billing_statement현재 발행 근거와 해시, 검토 이후 변경 여부, 재발행 필요 상태를 반환합니다.
runtime.transition_patient_billing_statement권한·청구 완료·해시·현재 상태를 검사하고 발행 준비 또는 발행을 처리합니다.
carebot.get_patient_billing_statement_history운영자·업체 범위 안에서 환자·월별 개정 이력을 조회합니다.
carebot.mutate_patient_billing_charge허용한 금액 종류의 추가·수정·삭제·복원을 처리하고 요청 ID와 변경 결과를 기록합니다.

검토한 자료와 발행할 자료가 같은지 확인

발행 시점에 원천 자료로 해시를 다시 계산해 요청의 source_hash와 비교합니다. 준비 상태의 근거와 현재 근거가 달라졌으면 충돌로 처리합니다. 업무 API는 검증·상태 변경을 한 트랜잭션으로 처리하고, 실패하면 롤백합니다.

같은 업체·환자·청구월의 상태 전이는 pg_advisory_xact_lock으로 순서를 맞추고, 대상 청구 주기와 내역서는 FOR UPDATE로 잠급니다. 반복 요청에는 이미 준비되거나 발행된 결과를 반환하는 경로를 두었습니다.

발행본 보존과 재발행

발행 시점의 내용은 payload_snapshot에 저장합니다. DB 트리거는 ISSUED 행의 수정·삭제와 잘못된 상태 전이를 거부합니다. 이후 근거가 바뀌면 기존 발행본을 보존하고 revision_no와 supersedes_statement_id로 새 개정본을 연결합니다.

금액 조정 요청의 중복 처리

금액 조정 API는 X-Request-ID를 요구합니다. DB 함수는 요청 ID와 운영자·업체·대상·입력 해시를 비교합니다. 같은 요청의 재시도에는 변경을 중복 적용하지 않고 처리 결과를 반환하며, 같은 ID에 다른 입력이 들어오면 REQUEST_ID_CONFLICT로 거부합니다.

05

API와 DB 권한

브라우저 입력과 운영자 문맥의 구분

Cloudflare Access로 확인한 사용자를 활성 운영자와 연결하고, 서버에서 operator_id와 vendor_id를 정합니다. 브라우저가 보낸 운영자·업체 값은 발행 요청의 신원 근거로 사용하지 않습니다. DB 제한 함수도 활성 HUMAN 운영자, MANAGER 이상 역할과 소속 업체를 확인합니다.

함수별 실행 권한

앱 계정의 청구내역서 기본 테이블 직접 변경 권한을 철회하고, 허용한 함수의 EXECUTE 권한을 부여했습니다. 함수 소유자는 nhis_migrator로 고정하고 SECURITY DEFINER, search_path = pg_catalog와 스키마를 명시한 참조를 사용합니다.

표는 migration과 권한 계약 검사에서 정의한 함수 실행 범위입니다. 상태 전이 함수는 두 운영 계정에 허용돼 있지만, 현재 콘솔의 발행 라우트는 NHIS 업무 API를 거치도록 구성했습니다. 환자용 조회 함수는 연결된 환자의 발행 완료본만 반환합니다.

업무 API 계정의 권한 설정 예시
REVOKE ALL ON runtime.patient_billing_statements FROM nhis_app;
GRANT SELECT ON runtime.patient_billing_statements TO nhis_app;

GRANT EXECUTE ON FUNCTION
  runtime.transition_patient_billing_statement(
    uuid, uuid, uuid, text, text, text
  ) TO nhis_app;

실제 migration의 권한 설정 중 일부입니다. 직접 DML 대신 함수 내부의 권한·업무 검사를 거쳐 상태를 변경합니다.

실패 원인을 구분하는 API 응답

상황처리
권한이 부족한 운영자의 요청API와 DB 역할 검사에서 거부하고 403으로 전달합니다.
검토 이후 계산·발행 근거 변경발행을 진행하지 않고 409 충돌로 전달해 다시 확인하도록 합니다.
현재 계산 API를 사용할 수 없음현재 금액 조회 실패를 표시합니다. 저장된 금액을 최신 계산값으로 대체하지 않습니다.
요청 ID 누락·충돌조정 API는 ID 누락을 DB 호출 전에 400으로 거부하고, DB의 요청 ID 충돌은 409로 전달합니다.
06

계약 검증과 기여

화면에 필요한 값을 반환하는 것과 함께, 허용하지 않은 호출과 변경 이후의 결과를 확인하는 계약 검사를 두었습니다. API 경로와 DB 권한·상태 전이 검사를 구분했습니다.

검사 구분확인하는 내용
콘솔 API 모의 계약서버의 운영자·업체 문맥 사용, STAFF 차단, 요청 ID 필수, 발행 API 전달, 계산 장애 시 대체값 금지, 기본 테이블 직접 DML 부재. 2026.10.18 소스 기준 27개 항목을 가상 DB·HTTP로 확인했습니다.
PostgreSQL 권한 계약has_function_privilege와 카탈로그 ACL을 조회해 역할별 함수 실행 허용·거부와 PUBLIC 실행 권한 부재를 검사하는 코드가 있습니다.
업무 상태·재시도 계약준비 이후 근거 변경, 발행본 보존·재발행, 추가 금액 조정, 동일 요청 재시도와 입력 충돌을 다루는 DB 계약 검사 코드가 있습니다.
화면 확인실제 청구내역서 컴포넌트에서 가상 자료의 발행 준비·발행·금액 조정·재발행 이력을 확인했습니다. 이 화면 확인은 운영 DB 검증과 구분합니다.

제 담당 범위

청구 업무 조건과 데이터 의미 정리, DB 모델·제한 함수·상태 전이 규칙, API·권한 계약 검토, 백엔드·배치 처리와 결과 확인을 담당했습니다. SQL·Python 구현에는 AI 코딩 도구를 활용했습니다.

협업과 구현 범위

콘솔 UI는 협업 결과물입니다. 청구내역서의 데이터 구조와 발행·재발행 계약을 화면과 맞췄으며, 기존 청구 업무 전체를 관리자 웹으로 통합하는 작업은 진행 중입니다.
