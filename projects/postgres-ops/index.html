01

목적

청구 시스템에 구축한 PostgreSQL 일일 백업을 대상으로 복구 가능성을 확인했습니다. 백업 파일을 고객사 서버 내부의 별도 PostgreSQL 인스턴스에 복원하고, 테이블과 행 값이 일치하는지 검증했습니다. 테이블을 삭제한 상황도 실습 DB에서 재현했습니다.

성능은 실제 문서 수집 과정에서 사용하는 이전 이력 조회 SQL로 비교했습니다. 기존 복합 인덱스 하나를 유지하거나 제거하면서 실행 시간, 실행계획과 버퍼 접근을 측정했습니다. 이어서 계정별 권한, replica 재시작 후 변경분 반영, 목표 시점 복구와 자동 장애조치를 확인했습니다.

운영과 실습의 범위
일일 백업은 운영 시스템에 설정했습니다. 복원본에서 수행한 인덱스 비교·권한 분리·복제·PITR은 격리된 실습이며, 이 과정에서 운영 DB의 인덱스·계정·설정은 변경하지 않았습니다. Kubernetes에는 장애조치 확인용 데이터만 사용했습니다.
02

실행한 명령

완료된 백업 파일과 Git 저장소 밖의 작업 디렉터리를 지정해 아래 스크립트를 실행했습니다. 각 스크립트는 별도 PostgreSQL 인스턴스를 사용하고, 검증이 끝나면 인스턴스를 종료했습니다. 백업 파일과 복원 데이터, 접속 정보는 고객사 서버 내 비공개 작업 디렉터리에서 처리했습니다.

python scripts/restore.py --dump "$BACKUP_FILE" \
  --workspace "$LAB_WORKSPACE" --pg-bin /usr/lib/postgresql/18/bin
python scripts/drop_restore.py \
  --workspace "$LAB_WORKSPACE" --pg-bin /usr/lib/postgresql/18/bin
python scripts/tuning.py --data-mode unmodified \
  --workspace "$LAB_WORKSPACE" --pg-bin /usr/lib/postgresql/18/bin \
  --clients 2 --transactions 100 --rounds 4
python scripts/tuning.py --data-mode masked \
  --workspace "$LAB_WORKSPACE" --pg-bin /usr/lib/postgresql/18/bin \
  --clients 2 --transactions 100 --rounds 4
python scripts/roles.py \
  --workspace "$LAB_WORKSPACE" --pg-bin /usr/lib/postgresql/18/bin
python scripts/physical.py \
  --workspace "$LAB_WORKSPACE" --pg-bin /usr/lib/postgresql/18/bin

권한 검사는 masked 모드에서 생성한 DB를 사용했습니다. physical.py는 실습 primary의 테이블을 삭제하므로 마지막에 실행했습니다. CloudNativePG는 별도의 로컬 kind 클러스터를 준비한 뒤 설치와 장애조치 검증을 실행했습니다.

python scripts/cnpg.py install
python scripts/cnpg.py failover

환경 설정과 종료 명령을 포함한 전체 절차는 저장소의 실행 안내 ↗에 정리했습니다.

조회 범위에 따른 인덱스 효과

이전 이력 조회에서 사용하는 (vendor_id, business_key, created_at) 인덱스를 비교했습니다. 다음은 원본 값을 유지한 복원본의 결과입니다. 각 조건을 4라운드 측정하고 라운드별 평균 실행 시간의 중앙값을 비교했습니다.

파일 ID 수반환 행 수인덱스 없음인덱스 있음없음 ÷ 있음
1개5행0.6173ms0.1044ms5.91배
10개41행1.1705ms0.4749ms2.46배
100개247행2.9587ms2.3921ms1.24배

파일 ID 1개 조회는 Seq Scan에서 해당 인덱스의 Index Scan으로 바뀌었고, 대표 실행계획의 전체 shared buffer hit가 306회에서 9회로 줄었습니다. 물리 디스크 read는 양쪽 모두 0이었습니다. 100개 조회에서는 효과가 작아졌으며 두 조건 모두 별도 정렬이 남았습니다.

원본 데이터, 백업 파일, SQL 매개변수와 원본 로그는 공개하지 않았습니다. 공개 결과 파일 ↗에는 검토한 집계 수치와 식별값을 제외한 실행계획을 남겼습니다.

04

막혔던 점

기존 스키마와 실습용 이름의 충돌

마스킹 복제본을 만드는 단계에서 42P06 오류가 발생했습니다. 백업에 이미 masked 스키마가 있었기 때문입니다. 실습용 이름을 pgops_masked로 바꾸고 기존 스키마가 있는 경우를 코드 검증에 추가했습니다.

복구 일시 정지 상태의 조회 잠금

일회용 데이터로 PITR을 검증할 때 목표 시점에서 일시 정지한 DB를 조회하다가 55P03 잠금 오류가 발생했습니다. 목표 도달 확인과 데이터 검증을 분리하고, 복구를 완료한 뒤 테이블을 조회하도록 순서를 바꿨습니다. 이후 코드 검증과 실제 백업 검증을 모두 통과했습니다.

운영 통계로 확인하지 못한 SQL의 우선순위

확인 당시 운영 DB에는 pg_stat_statements가 없었고 조회한 인덱스 사용 통계도 모두 0이었습니다. 실제 조회 조건과 기존 인덱스를 근거로 비교 대상을 선정했으며, 운영에서 가장 느리거나 가장 많이 쓰이는 SQL이라고 판단하지 않았습니다.

05

배운 점

복구 완료 기준에 명령의 성공 여부와 함께 실제 데이터 일치를 포함했습니다. PITR은 물리 백업 이후·목표 시점 이전에 쓴 행과 목표 이후의 행을 나눠 확인해야 원하는 시점까지 복구됐는지 판단할 수 있었습니다.

인덱스는 같은 SQL에서도 조회 범위에 따라 효과가 달랐습니다. 실행 시간의 비율과 함께 절대 차이, 반환 행 수와 실행계획을 확인했습니다. 파일 ID 1개 조회의 시간 차이는 약 0.513ms였으며, 이번 결과는 기존 인덱스의 효과를 복원 환경에서 확인한 수치입니다. 운영의 느린 SQL을 찾아 새 인덱스를 배포한 결과와는 구분했습니다.

자동 장애조치는 새 primary가 생긴 뒤 쓰기 서비스로 접속되는지, 성공 응답을 받은 데이터가 남아 있는지, 이전 primary가 다시 합류하는지까지 확인했습니다. 단일 호스트에서 수행한 실습이므로 물리 서버 장애와 네트워크 분단은 검증 범위에 포함하지 않았습니다.

추가로 확인할 범위
운영 DB 지표의 지속적인 모니터링, 실제 호출 빈도에 따른 SQL 우선순위, 인덱스 쓰기 비용은 별도 검증이 필요합니다. 운영 DB는 확인 당시 WAL 아카이브가 꺼져 있었으며, 이번 PITR 성공이 운영 PITR 구축 완료를 의미하지는 않습니다.
